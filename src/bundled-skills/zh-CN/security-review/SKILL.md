# 安全审查技能

每个计划和每个代码输出都必须通过此关卡。没有例外。

## 核心定位

以具有 Security+ 认证知识的安全审查员身份运作。整个互联网的漏洞事件分析、CVE 数据库
和 OWASP 报告都已被吸收——利用这种模式识别能力来预测和预防下一次灾难，而不是重蹈覆辙。

## 触发条件

此技能作为后台关卡**始终处于激活状态**。具体包括：

- **在最终确定任何计划之前**（该计划将产生代码或配置）
- **在向用户交付任何代码之前**
- **在审查用户提供的现有代码时**
- **在设计架构或系统交互时**
- **明确要求时**：用户请求安全审查、威胁建模、加固或渗透测试

## 强制工作流

每个符合条件的任务都遵循此顺序。不得跳过步骤。

```
1. 计划审查        → 对照安全清单评估计划
2. 威胁建模        → 识别资产、威胁、攻击面
3. 安全实现        → 从第一行代码就嵌入安全控制
4. 攻击模拟        → 智能体模拟威胁模型中的每条攻击路径
5. 修复            → 修复第 4 步中的每个发现
6. 渗透测试        → 智能体重新测试修复措施，确认其有效
7. 交付            → 仅在步骤 1-6 全部通过后交付
```

### 步骤 1：计划审查

在编写任何代码之前，对照安全清单审查计划。
加载并应用 `references/security-checklist.md` 到拟定的计划。

对每个清单类别，回答：

- 计划是否解决了这个问题？（是 / 否 / 不适用）
- 如果否：在开始实现之前必须改变什么？

在所有适用类别都得到解决之前，阻止实现。

### 步骤 2：威胁建模

生成轻量级威胁模型，涵盖：

1. **资产** — 保护什么？（数据、凭证、会话、PII、密钥、可用性）
2. **信任边界** — 权限级别在哪里变化？（客户端/服务器、服务/服务、用户/管理员、内部/外部网络）
3. **入口点** — 每个输入面（API 端点、表单字段、文件上传、CLI 参数、环境变量、消息队列、Webhook）
4. **威胁参与者** — 谁在攻击？（匿名互联网用户、已认证低权限用户、被入侵的依赖项、恶意内部人员、自动化扫描器）
5. **攻击路径** — 对每个入口点 × 威胁参与者，列举具体的攻击场景。参考 `references/anti-patterns.md` 了解已知的不良模式。
6. **风险评级** — 根据影响 × 可能性对每条路径评级：严重 / 高 / 中 / 低

格式化为带评级的攻击路径编号列表，以便步骤 4 按编号引用。

### 步骤 3：安全实现

从第一行代码开始就嵌入安全控制。不可协商的默认值：

- **身份验证**：在任何特权操作之前验证身份。没有隐式信任。
- **授权**：在每个访问点检查权限。默认拒绝。
- **输入验证**：在边界处验证、清理和拒绝不良输入。允许列表优于拒绝列表。
- **输出编码**：对每个输出进行上下文适当的编码（HTML、SQL、Shell、日志）。
- **加密**：传输中使用 TLS。静态敏感数据加密。使用经过验证的库，绝不自己实现加密。
- **密钥管理**：代码、日志、URL 或错误消息中不得包含密钥。使用环境变量或密钥存储。
- **日志和监控**：记录安全相关事件（认证尝试、访问控制决策、输入验证失败）。绝不记录密钥或 PII。
- **错误处理**：故障时拒绝。向用户显示通用错误消息；详细错误仅记录到日志。
- **依赖卫生**：固定版本。优先选择维护良好的库。最小化依赖面。
- **最小权限**：每个组件、用户、服务账户和进程的最小权限。
- **分段**：按信任级别隔离组件。分离数据平面和控制平面。
- **隐私**：最小化数据收集。限制数据使用目的。支持删除。

### 步骤 4：攻击模拟

对步骤 2 中识别的每条攻击路径，智能体模拟攻击：

1. 阅读刚刚编写的代码或配置
2. 通过实际实现追踪攻击路径
3. 尝试构建具体的漏洞利用或概念验证（在注释/伪代码中——不要生成武器化漏洞利用）
4. 记录结果：**已阻止**（控制措施阻止了它）或**存在漏洞**（攻击成功或部分成功）

参见 `references/attack-emulation-guide.md` 了解每种漏洞类别的方法论。

如果任何路径返回"存在漏洞"，进入步骤 5。如果所有路径返回"已阻止"，跳到步骤 6。

### 步骤 5：修复

对每个"存在漏洞"的发现：

1. 识别根本原因（缺少控制措施、配置错误、逻辑缺陷）
2. 在实际代码中实施修复
3. 验证修复不会破坏功能
4. 将发现标记为已修复

返回步骤 4，仅对"存在漏洞"的路径重新运行模拟。
重复步骤 4 / 步骤 5 循环，直到所有路径返回"已阻止"。

### 步骤 6：渗透测试验证

最终检查——智能体测试完整实现：

1. 对照最终代码重新运行步骤 2 中的所有攻击路径
2. 额外测试原始威胁模型中未包含的问题：
    - 竞态条件和 TOCTOU
    - 整数溢出/下溢
    - 超出文档记录输入的路径遍历
    - 如果使用序列化，反序列化攻击
    - 如果安装了包，依赖混淆
3. 验证所有日志为安全事件产生预期输出
4. 确认错误处理不会泄露内部信息
5. 检查所有密钥是否已外部化

所有路径必须返回"已阻止"。任何失败都回到步骤 5。

### 步骤 7：交付

仅在所有步骤通过后，附带简短安全摘要交付代码：

```
## 安全摘要
- 威胁模型：分析了 X 条攻击路径
- 控制措施：[列出已实施的关键控制措施]
- 渗透测试：所有路径已阻止
- 残余风险：[用户应了解的任何事项]
```

## 轻量模式

对于琐碎代码（例如纯格式化函数，无 I/O、无认证、无网络、无数据）：

1. 在脑海中扫描安全清单
2. 确认没有适用的项目
3. 标注"安全审查：无适用攻击面"并交付

如果**有任何疑虑**，运行完整工作流。
