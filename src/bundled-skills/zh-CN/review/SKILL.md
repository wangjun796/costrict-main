# 代码审查技能

执行超越表面检查的全面代码审查。

## 核心定位

以资深工程师的身份进行深入的代码审查。你在多种语言、框架和架构方面拥有丰富的经验。
你的审查具有建设性、具体且可操作 —— 你不仅指出问题所在，还解释为什么重要以及如何修复。

## 触发条件

- 用户明确要求代码审查时
- 审查拉取请求或合并请求时
- 用户要求审查特定文件或代码片段时
- 调用 `/review` 命令时

## 审查工作流

```
1. 确定范围     —— 确定审查内容和审查重点
2. 分析代码     —— 深入阅读和理解代码
3. 执行审查     —— 应用多维度分析
4. 生成报告     —— 输出结构化审查结果
5. 提出建议     —— 提供具体的改进建议
```

### 第一步：确定范围

在审查之前，明确：

1. **审查什么？**（单个文件、PR 差异、整个模块、完整项目）
2. **关注领域** —— 是否有特定关注点？（安全、性能、正确性、风格）
3. **上下文** —— 适用哪些框架、语言版本、编码规范？

如果用户未指定，默认进行全面综合审查。

### 第二步：分析代码

在做出任何判断之前，仔细阅读代码：

1. 理解**意图** —— 这段代码试图实现什么？
2. 追踪**数据流** —— 输入来自哪里，输出流向哪里？
3. 识别**依赖** —— 涉及哪些外部系统、库或服务？
4. 注意**假设** —— 代码对其环境或输入做了哪些假设？
5. 检查**错误处理** —— 代码如何处理失败和边界情况？

### 第三步：审查 —— 多维度分析

系统地应用以下审查维度：

#### 3.1 正确性

- 代码是否按预期工作？
- 是否存在差一错误、空指针风险、类型不匹配？
- 是否处理了边界情况？（空输入、边界值、并发访问）
- 是否存在竞态条件或死锁？
- 逻辑是否正确处理了所有分支？

#### 3.2 安全性

- 信任边界处的输入验证和清理
- SQL 注入、XSS、CSRF、命令注入风险
- 是否进行了身份验证和授权检查？
- 密钥管理 —— 是否有硬编码的凭据？
- 错误处理是否恰当，不会泄露敏感信息？
- 依赖项是否没有已知漏洞？

#### 3.3 性能

- 不必要的循环、冗余计算、N+1 查询？
- 内存泄漏或过度分配？
- 数据库查询效率 —— 索引是否合理、是否使用批量操作？
- 是否错过了缓存机会？
- I/O 操作是否可以异步或批量处理？

#### 3.4 可维护性

- 命名是否清晰 —— 名称是否传达了意图？
- 函数/方法的长度和复杂度 —— 是否职责单一？
- 代码重复 —— 逻辑是否可以提取和复用？
- 注释 —— 是否解释了"为什么"而不仅仅是"是什么"？
- 风格和格式是否一致？

#### 3.5 架构与设计

- 关注点分离 —— 职责是否明确？
- 抽象层次是否恰当 —— 不过度也不欠缺？
- 依赖方向 —— 依赖关系流向是否正确？
- 可测试性 —— 代码是否易于测试？
- 是否遵循了适用的 SOLID 原则？

#### 3.6 测试

- 是否有测试？是否覆盖了正常路径和边界情况？
- 测试质量 —— 是有意义的测试还是仅仅追求覆盖率数字？
- Mock/Stub 的使用是否恰当？
- 关键路径是否有集成测试覆盖？

#### 3.7 嵌入式系统与 C/C++

当被审查代码为 C、C++ 或面向嵌入式/固件（MCU、RTOS、裸机、驱动、BSP）时，
应用以下额外维度，并加载 `references/embedded-c-cpp-checklist.md` 中的详细清单：

- **内存安全** —— 热路径/中断路径中无动态内存分配、栈使用量可预测、无缓冲区越界、
  无 use-after-free、无内存泄漏、所有 `memcpy`/`strcpy`/`sprintf` 均做边界检查。
- **整数与类型安全** —— 无有符号/无符号混用、无隐式窄化、溢出/下溢有防护、
  硬件相关数据使用定宽类型（`uint8_t`..`uint32_t`）、不依赖平台字长（嵌入式中 `int` 可能为 16 位）。
- **未定义行为** —— 移位宽度不超出类型、无有符号溢出、不解引用 NULL/未初始化指针、
  不读取未初始化内存（上电时 RAM 内容不确定）。
- **并发与中断** —— ISR 尽量短且不阻塞、ISR 与主循环共享数据用 `volatile` + 原子操作/临界区保护、
  无优先级反转、无死锁、ISR 内不使用 `printf`/`malloc`。
- **硬件交互** —— MMIO/寄存器访问使用 `volatile`、读-改-写为原子操作、处理字节序与对齐、
  看门狗喂狗逻辑正确、外设初始化与错误路径完整。
- **可移植性** —— 不假设 `char` 的有符号性、不依赖字节序、不依赖实现定义行为。
- **标准符合性** —— 标记 MISRA C:2012/2023（Required/Advisory）与 CERT C/C++ 规则违反项，
  并给出规则编号与修复建议。

### 第四步：报告

生成结构化的审查报告：

```markdown
## 代码审查报告

### 概述

简要概述审查内容和整体评估。

### 严重问题（必须修复）

可能导致数据丢失、安全漏洞或系统故障的问题。

### 重要问题（建议修复）

显著影响正确性、性能或可维护性的问题。

### 改进建议（可选）

能提升代码质量但非阻塞性的改进。

### 亮点

代码做得好的地方 —— 认可良好的模式和做法。

### 指标

- 审查文件数：X
- 发现问题：X 个严重，X 个重要，X 个建议
- 测试覆盖率：X%（如适用）
```

### 第五步：建议

对于发现的每个问题：

1. **引用问题代码** —— 明确指出位置
2. **解释问题** —— 为什么这是问题？可能出什么错？
3. **评定严重程度** —— 严重 / 重要 / 建议
4. **提供修复方案** —— 展示修正后的代码或描述修复方法
5. **引用标准** —— 链接到相关的指南或最佳实践

## 审查经验法则

在审查过程中应用以下经验法则：

- **如果难以理解，很可能有问题** —— 复杂性会隐藏 bug
- **如果难以测试，设计需要改进** —— 可测试性意味着良好的架构
- **如果无法解释数据流，说明存在缺口** —— 不清晰的数据流意味着不清晰的逻辑
- **如果缺少错误处理，生产环境必然失败** —— 假设一切都会出错
- **如果没有测试，代码未经证实** —— 未测试的代码就是有问题的代码

## 嵌入式与 C/C++ 项目

审查 C/C++（或嵌入式/固件）代码时，务必：

1. **加载** `references/embedded-c-cpp-checklist.md`，将其中的 MISRA C 与 CERT C 分类
   与第 3.7 节的维度一并应用。
2. **运行静态分析**：当存在源文件时调用 cppcheck，将其确认的发现合并进报告作为证据
   （引用 cppcheck 检查编号，如 `[shiftTooManyBits]`）。

### 调用 cppcheck

按以下顺序定位 cppcheck 可执行文件：

1. **系统安装** —— 运行 `cppcheck --version`，若打印出版本号则直接使用 `cppcheck`。
2. **内置便携版** —— 否则扩展在安装目录下内置了 cppcheck，路径为
   `assets/cppcheck/win32-x64/cppcheck.exe`。在 VS Code 扩展目录下用 glob 搜索
   `**/assets/cppcheck/win32-x64/cppcheck.exe`（Windows 为 `~/.vscode/extensions`，
   远程/WSL 为 `~/.vscode-server/extensions`）。

推荐调用方式（C）：

```bash
cppcheck --enable=all --inconclusive --std=c11 --suppress=missingIncludeSystem <文件或目录>
```

对于嵌入式目标，加上匹配的 ABI 平台，以便正确检查整数位宽/字节序：

```bash
cppcheck --enable=all --inconclusive --std=c11 --platform=avr8 <文件>
# 平台：avr8、msp430、pic8、pic16、arm32-wchar_t4、arm64、riscv32、riscv64 等
```

C++ 使用 `--std=c++17 --language=c++`。需要机器可解析输出时可加 `--xml` 或 `--template=gcc`。
忽略 `missingIncludeSystem` 信息类消息；将 `error`/`warning`/`portability` 级别视为高价值发现。

结合清单解读结果：将 cppcheck 检查编号映射到 CERT/MISRA 规则（清单中包含映射表），
对每个确认的缺陷引用代码、说明风险、评定严重程度并给出修复方案。cppcheck 是辅助工具，
存在误报，因此在作为问题上报前必须逐条对照源码核实。

## 轻量模式

对于小型变更（1-10 行，简单修复）：

1. 快速扫描明显问题
2. 检查特定变更是否正确
3. 如果没有问题，注明"审查：未发现显著问题"
4. 简要标记任何疑虑

如果变更涉及安全关键代码、错误处理或并发 —— 无论大小，始终进行完整审查。

## 输出格式

始终使用用户偏好的语言输出。默认使用代码库或用户请求中使用的语言。
