## 独立验证 Ollama starcoder2:3b + 插件不能补全根因分析

用户贴了独立的 Python 测试脚本（POST `/api/generate`，`raw=true`，`num_predict=80`，无 suffix）并通过 → 证明**模型层本身可达、能返回补全**。

随后对比插件实际请求（`src/core/costrict/auto-complete/fim/completionEngine.ts` `sendOllamaCompletion`）与测试脚本，并写了独立探针 `scripts/probe-plugin-ollama.mjs` 复刻插件请求格式：

**根因 A（立即/硬阻塞）：本机内存不足，starcoder2:3b 加载即 OOM**

- 探针与单次干净请求均返回 `500` + `failed to allocate CPU_REPACK buffer of size 1704001536`（约 1.7GB 连续 CPU 内存不足）。
- 用户 Python 测试"通过"是内存够的那一刻；之后（含我连发多条探针）触发 OOM，`llama-server process has terminated`。
- 这是代码无法修复的环境问题：需释放内存 / 重启 `ollama serve` / 用更小模型（如已装的 qwen3.5:2b）/ 上 GPU。

**根因 B（配置/软阻塞）：插件默认超时 3000ms ≪ CPU 推理耗时**

- 插件默认 `fim.maxOutputTokens=256`，CPU-only ~6 tok/s → 约 40s 才返回，但 `fim.timeoutMs` 默认仅 3000ms。
- 每次请求都被插件自己 `setTimeout` 取消 → 日志里那串 `Ollama request cancelled`（已在上一轮把 timeoutMs=0 支持加上，需用户在设置里把 fim.timeoutMs 设 0）。

**根因 C（正确性）：插件 Ollama 分支此前未设 `raw:true`**

- 用户通过的测试显式 `raw=true`；对 starcoder2 这类 base 代码模型，raw=true 跳过 Ollama 默认模板、直接用 prompt 是正确的。
- 已修改 `sendOllamaCompletion` 在 body 中加 `raw: true`（待内存恢复后实测验证；FIM 走 `/api/generate`+`suffix` 是否受 raw 影响需确认，必要时改走 `/v1/completions`+内嵌 `<fim_*>` 标记）。

**待验证（内存恢复后）**：光标在代码中间（suffix 非空）时，/api/generate+suffix 与 /v1/completions+内嵌 FIM 标记 哪种格式返回的中间补全更稳。

探针脚本 `scripts/probe-plugin-ollama.mjs` 修复了"无超时"误用 `setTimeout(...,0)` 会立即自取消的 bug（现 timeoutMs<=0 不挂定时器），可复现：纯前缀续写、插件当前路径(+suffix/无raw对比+raw)、默认3s超时必取消、/v1/completions 替代方案 四个场景。

## 修复 deepseek-coder:1.3b "does not support insert" (400)

现象：插件用 `/api/generate` + `suffix` 走 Ollama FIM，但 `deepseek-coder:1.3b` 这个 Ollama 镜像未声明 `insert` 能力，返回 `400 {"error":"...deepseek-coder:1.3b does not support insert"}`；`starcoder2` / `deepseek-coder-v2` 支持所以正常。

修复（completionEngine.ts `sendOllamaCompletion`）：`postOnce` 内遇到 `status===400 && /does not support insert/i/ && suffix非空` 时返回哨兵 `"INSERT_UNSUPPORTED"`；函数先试原生 insert，若返回该哨兵则用 `getFimMarkers(config)` 把 FIM 标记拼进 prompt、去掉 suffix 字段、保持 `raw:true` 重试一次（`begin+prompt+hole+suffix+end`）。

同时修正 `types.ts` 中 `FIM_MARKERS.deepseek` 错误：原 `hole:"<｜fimhole｜＞"` / `end:"<｜fimend｜＞"` 少了 `▁`，正确应为 `＜｜fim▁hole｜＞` / `＜｜fim▁end｜＞`（与 `begin` 一致，全角括号 + `▁` 空格符）。DeepSeek FIM 标记经搜索确认是 `＜｜fim▁begin｜＞`/`＜｜fim▁hole｜＞`/`＜｜fim▁end｜＞`（Ollama deepseek-coder-v2 模板与 HF 文档一致）。注意 EOS `＜｜end▁of▁sentence｜＞` 原已正确。

验证：`src` tsc --noEmit 通过。本机仍 OOM，未做运行期实测；逻辑上等同于 Ollama 自身对支持 insert 的模型所做的模板包装（`{{- if .Suffix }}＜｜fim▁begin｜＞{{.Prompt}}＜｜fim▁hole｜＞{{.Suffix}}＜｜fim▁end｜＞{{ end }}`）。

## 分析：为何"报错但补全成功" + 是否需要 tokenizer

用户追问：(a) 为什么没有真实 tokenizer 也能工作；(b) 是否需要加 tokenizer；(c) deepseek-coder:1.3b 即使没 insert 能力也要能走 FIM 填空；(d) 为什么日志报错但补全成功了。

结论与解释：

- **"报错但补全成功" = 回退重试的预期行为，不是 bug**。旧代码把 `does not support insert` 的 400 当致命错误（completionError→返回 null→整条失败）。新代码在 `sendOllamaCompletion` 捕获该特定 400 返回哨兵 `INSERT_UNSUPPORTED`，随后用「内嵌 FIM 标记 + raw:true + 去掉 suffix」重试一次并成功。日志里的报错=第一次 insert 尝试；补全=成功的回退重试。
- 已补一条 `completionWarn`（非错误级）说明"falling back to embedded FIM markers"，重新打包后旧版那条刺眼的 `Ollama request failed` 应消失、改为该 WARN。
- **内嵌 FIM 能工作**的机理：`raw:true` 让 Ollama 不套 chat 模板、按原始文本 tokenize；deepseek-coder 词表注册了 `＜｜fim▁begin｜＞/＜｜fim▁hole｜＞/＜｜fim▁end｜＞` 等特殊 token，Ollama 用模型自带 tokenizer 把它们识别为 special token→模型进入 FIM 模式→在 prefix/suffix 间生成 middle。这与该模型训练格式一致。
- **没有真实 tokenizer 也能工作**：插件只拼接文本 prompt（标记+prefix+suffix），真正的 tokenize 在 Ollama 服务端完成（发文本，Ollama 转 token id）；generic TGI/OpenAI 路径同理。preprocess.ts 的 `estimateTokens=ceil(len/4)` 纯字符估算，仅影响截断/预算精度，不影响"能否补全"。
- **是否需要加 tokenizer**：不建议引入完整 JS tokenizer（sentencepiece/tokenizers，重依赖+词表文件+体积/性能+与服务端双份真相风险）。更优做法：用 Ollama 现成 `POST /api/tokenize` 拿精确 token 数（服务端权威），仅在需要精确预算/debug 时调用，平时仍用 length/4 兜底；本地模型路径模型自带 tokenizer。
- 残留验证点：内嵌回退是否产生"真正填空"而非"前缀续写"，需开 fim.debug 看 completion 是否落在 prefix/suffix 之间且未被 removeSuffixOverlap 误删；用户实测"补全成功"说明方向正确。
